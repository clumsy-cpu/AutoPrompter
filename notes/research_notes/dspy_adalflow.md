Source pin: stanfordnlp/dspy commit bc8af7ed (shallow clone, read raw). Permalink base: https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/ . Evidence type: CODE = read from source; PAPER = arXiv preprint (MIPROv2 paper is EMNLP 2024 per its venue, not verified here -> treat as preprint).

## 1. Loop structure (MIPROv2, COPRO, BootstrapFewShot(+RandomSearch), SIMBA)

### Takeaway
MIPROv2 is NOT an iterative critique loop: it generates a fixed pool of instruction candidates and demo-set candidates up front, then searches combinations with Optuna TPE over minibatch scores, with periodic full evals on a valset. COPRO is closest to ours (iterative, attempts+scores history) but breadth-parallel and scored on the trainset. SIMBA is the only DSPy optimizer that feeds per-example trajectories/failures to an LLM, and it is population-based with softmax sampling.

### Cited Findings
**MIPROv2** (dspy/teleprompt/mipro_optimizer_v2.py)
- Three stages in `compile()`: (1) bootstrap N demo sets, (2) propose N instruction candidates per predictor via GroundedProposer, (3) `_optimize_prompt_parameters` = Optuna search. Instructions are proposed ONCE up front, using only trainset-derived info (dataset summary, program code, bootstrapped demos, a tip); there is no feedback from candidate scores into proposals. — [mipro_optimizer_v2.py compile L130-250](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/mipro_optimizer_v2.py) (CODE)
- MIPRO constructs the proposer with `use_instruct_history=False, set_history_randomly=False`, so past-attempt scores are not shown to the proposer in MIPROv2 (the history machinery exists in GroundedProposer, used by other callers). — [mipro_optimizer_v2.py ~L470-490](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/mipro_optimizer_v2.py#L482) (CODE)
- Demo candidate sets: `create_n_fewshot_demo_sets` builds sets seeded -3..N-3: set -3 zero-shot, -2 labeled-only (LabeledFewShot), -1 unshuffled BootstrapFewShot, then shuffled BootstrapFewShot with random size in [1, max_bootstrapped_demos] (same recipe as BootstrapFewShotWithRandomSearch). Demos are bootstrapped from trainset by running the program (teacher) and keeping traces whose metric passes. — [teleprompt/utils.py L324-410](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/utils.py#L324)
- Search: `optuna.samplers.TPESampler(seed, multivariate=True)`, categorical params `{i}_predictor_instruction` and `{i}_predictor_demos`; default program (index 0 instruction, demo set 0) is evaluated fully on valset and injected into the study as a baseline trial. — [mipro_optimizer_v2.py L520-680](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/mipro_optimizer_v2.py#L658)
- Minibatch + periodic full eval: each trial scores a candidate on `minibatch_size` (default 35) random valset examples; every `minibatch_full_eval_steps` (default 5) trials, the not-yet-fully-evaluated param combination with highest MEAN minibatch score is evaluated on the full valset, added back into the Optuna study as a trial with the full score, and becomes best only if full score > best_score. A final full eval runs at the end. Returned program = highest FULL-eval score (minibatch scores never promote to best when minibatch=True). — [mipro_optimizer_v2.py L528-660, L800-866](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/mipro_optimizer_v2.py#L800) (CODE)
- `auto` presets: light `{n:6, val_size:100}`, medium `{n:12, val_size:300}`, heavy `{n:18, val_size:1000}`; valset is subsampled to val_size; minibatch on iff len(valset) > 50; `num_trials = int(max(2*num_vars*log2(n), 1.5*n))` with num_vars = n_predictors (x2 if demos used); instruction candidates = n/2 when demos enabled (comment: "better to spend optimization budget on few-shot examples"), few-shot candidates = n. If `auto` is set, num_candidates and num_trials may not be passed. — [mipro_optimizer_v2.py L44-52, L280-320](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/mipro_optimizer_v2.py#L46)
  - Worked numbers (computed from the formula, single predictor with demos so num_vars=2): light n=6 -> int(max(2*2*log2(6)=10.34, 9)) = 10 trials; medium n=12 -> int(max(14.34, 18)) = 18; heavy n=18 -> int(max(16.68, 27)) = 27. (My arithmetic from the code formula, not a doc quote.)
- Stopping: fixed `num_trials`; no early stop on stagnation. Defaults: max_bootstrapped_demos=4, max_labeled_demos=4, seed=9, init_temperature=1.0. — [mipro_optimizer_v2.py L52-100](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/mipro_optimizer_v2.py#L53)
- Population vs single: population of (instruction idx x demo idx) combos per predictor; Optuna proposes the next combo. Credit assignment is done by the surrogate, not the LLM (paper: "By separating the task of credit assignment from prompt proposal, we allow the proposal LM to focus on the task of proposal only"). — [MIPROv2 paper s4.3](https://arxiv.org/abs/2406.11695) (preprint)

**BootstrapFewShot** (dspy/teleprompt/bootstrap.py)
- Single pass, no iteration over scores: run teacher (default = copy of student) over trainset examples in order; for each, run program and call `metric(example, prediction, trace)`; if truthy (or >= `metric_threshold`) keep each predictor's (inputs, outputs) as a demo marked `augmented=True`; stop when `max_bootstrapped_demos` (default 4) collected. Remaining unbootstrapped train examples are shuffled and up to `max_labeled_demos` (default 16) minus bootstrapped are added as raw labeled demos. `max_rounds` (default 1) retries with temperature=1.0 rollouts. — [bootstrap.py L60-272](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/bootstrap.py#L95) (CODE)
- Only demos change; instruction text is untouched. Metric is never optimized against by search; it is just a filter. The metric receives the example's own demo removed from teacher demos to avoid trivial copying (`predictor.demos = [x for x in predictor.demos if x != example]`). — [bootstrap.py _bootstrap_one_example](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/bootstrap.py#L172)

**BootstrapFewShotWithRandomSearch** (dspy/teleprompt/random_search.py)
- For seed in range(-3, num_candidate_programs=16): -3 zero-shot, -2 labeled-only, -1 unshuffled bootstrap, >=0 shuffled trainset with random number of bootstrapped demos in [1, max_bootstrapped_demos]. Each candidate is scored with `Evaluate` on `valset`; best score wins; `stop_at_score` for early stop. All candidates attached sorted as `best_program.candidate_programs`. — [random_search.py L29-168](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/random_search.py#L58) (CODE)
- If no valset passed: `self.valset = valset or trainset` with a code comment "TODO: FIXME: Note this choice" - i.e. it silently selects on the same data demos came from. — [random_search.py L59](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/random_search.py#L59)

**COPRO** (dspy/teleprompt/copro_optimizer.py)
- Iterative breadth x depth loop, instruction + output-prefix only (no demos change). Init: LLM generates `breadth-1` (default breadth=10) variants of the basic instruction at `init_temperature=1.4`; original added as candidate. For each depth d (default depth=3): evaluate every candidate on `trainset` via `Evaluate`; keep dict of evaluated candidates keyed (instruction, prefix) (keeps higher score on repeat); set the predictor to the best-scoring candidate; then build a prompt of past attempts sorted ascending by score ("Instruction #k / Prefix #k / Resulting Score #k") and ask `GenerateInstructionGivenAttempts` for `breadth` new instruction+prefix proposals. Final: all evaluated candidates sorted by score, dedup of equal-score equal-text, return best. — [copro_optimizer.py L60-356](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/copro_optimizer.py#L104) (CODE)
- Feedback to the proposer is ONLY (instruction text, prefix, scalar score) tuples, no failing examples or critiques. Signature docstring: "I will give some task instructions I've tried, along with their corresponding validation scores. The instructions are arranged in increasing order based on their scores..." — [copro_optimizer.py L50-60](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/copro_optimizer.py#L50) (CODE; the docstring says "validation scores" but the code scores on the `trainset` argument: `Evaluate(devset=trainset...)`.)
- Cost: depth x breadth full-trainset evaluations (default 3 x 10 = ~30 candidate evals, since each of `breadth` candidates is evaluated per depth) plus depth-1 proposal calls with n=breadth completions. `total_calls` counts metric evaluation passes. Usage comment suggests `trainset[:DEV_NUM]`. — [copro_optimizer.py usage docstring](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/copro_optimizer.py#L15)
- Dedup is only post-hoc at the end (`_drop_duplicates` among equal scores), not blocking re-evaluation of duplicates.

**SIMBA** (dspy/teleprompt/simba.py, simba_utils.py)
- Stochastic Introspective Mini-Batch Ascent. Defaults: bsize=32, num_candidates=6, max_steps=8, max_demos=4, temps 0.2. Per step: (1) take next bsize trainset batch (shuffled, cycling); (2) run bsize x num_candidates rollouts, each picking a program from top-k+baseline pool via softmax on mean minibatch score, with varied LM temperature/seed; (3) bucket by example, sort buckets by (max-min score gap, max score, max-avg gap) to find examples with high output variability; (4) for top buckets create a new candidate from a softmax-sampled parent, randomly drop demos (Poisson), then apply a random strategy: `append_a_demo` (add the best trajectory as a demo) or `append_a_rule` (LLM `OfferFeedback` contrasts better vs worse trajectory and appends advice text to the module instruction); (5) evaluate new candidates on the SAME minibatch; (6) best of the step recorded as "winning"; all registered into pool. End: pick ~7 evenly spaced winners and evaluate them on the FULL trainset, return highest. No valset argument. — [simba.py L79-377](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/simba.py#L79), [simba_utils.py L108-230](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/simba_utils.py#L108) (CODE)
- `append_a_rule` skips when good score <= 10th percentile of batch or bad score >= 90th percentile. The OfferFeedback input includes `oracle_metadata` ("Any (hidden) metadata about the training set instance", i.e. example.labels()) plus both trajectories, rewards, and metric feedback info; its docstring asks for advice that "balanc[es] being concrete and being generalizable" and "specific to that M's specific sub-task". — [simba_utils.py L143-187](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/simba_utils.py#L143) (CODE)

### Inferences
- Structural contrast with AutoPrompter: MIPROv2/BootstrapRS never let the LLM see failures; the proposer is blind to scores, so it cannot memorize labels into the instruction. Our Optimizer LLM sees failing examples with answers, which is the leakage channel. SIMBA is the closest DSPy analogue and passes labels (`oracle_metadata`) to its rule writer, relying only on a prompt-level "generalizable" instruction, with no code-level guard; I found no filter in code that blocks label strings in advice (absence of evidence from reading simba_utils.py only).
- COPRO and SIMBA both evaluate on the trainset they optimize on; only MIPROv2 (with valset) and RandomSearch (with explicit valset) have a separate selection set.

### Gaps
- Not verified: whether MIPROv2 paper is formally EMNLP 2024 (arXiv listing only fetched as PDF text).
- SIMBA has no paper I read; behaviour taken from code and docs only.

## 2. Feedback use, instruction proposal (GroundedProposer)

### Takeaway
MIPROv2's proposer sees: an LLM-written dataset summary of up to ~10 batches of trainset examples, the program source code and an LLM description of the program and module, up to 3 bootstrapped demos, a random "tip" style hint, and the basic instruction. It never sees scores or failures.

### Cited Findings
- Dataset summary: `create_dataset_summary` shows the prompt model `view_data_batch_size` (default 10) trainset examples at a time, up to 10 calls, accumulating observations (stops after 5 "COMPLETE" replies), then summarizes to 2-3 sentences. — [dataset_summary_generator.py](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/propose/dataset_summary_generator.py#L53) (CODE)
- Program awareness: `DescribeProgram` + `DescribeModule` signatures turn the program source (via `get_dspy_source_code`) and an example into descriptions fed to the instruction generator. — [grounded_proposer.py L25-60, L140-200](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/propose/grounded_proposer.py#L25)
- Tips: dict `TIPS` = none, creative, simple, description, high_stakes, persona (e.g. "Include a persona..."), chosen uniformly at random per candidate when `tip_aware_proposer` is set. — [grounded_proposer.py L15-23](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/propose/grounded_proposer.py#L15)
- Diversity mechanisms: each candidate uses a different demo set as in-context examples (`demo_set_i`, adjacent sets rotate), a random tip, temperature `init_temperature`=1.0 and a unique `rollout_id` to bypass the LM cache. Instruction 0 is overwritten with the original instruction. — [grounded_proposer.py L310-417](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/propose/grounded_proposer.py#L370), [mipro_optimizer_v2.py L492](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/mipro_optimizer_v2.py#L492)
- Paper: grounding = data summary, program summary, bootstrapped demos, tip; ablation "Lesson 4: Grounding is helpful for instruction proposal overall, but the best proposal strategy varies by task" (essential for HotPotQA and HoVer, seems to hurt ScoNe). Learned Bayesian importance: bootstrapped demos in meta-prompt and tip highest. — [arXiv 2406.11695 s6](https://arxiv.org/abs/2406.11695) (preprint)
- Metric plug-in: user function `metric(example, prediction, trace=None)`; `Evaluate` calls `metric(example, prediction)`; bootstrap calls `metric(example, prediction, trace)` and may use trace to be stricter during bootstrapping. Returns float/bool. — [evaluate.py L175](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/evaluate/evaluate.py#L175), [bootstrap.py L205](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/bootstrap.py#L205)

### Inferences
- A MIPRO-style instruction proposer that sees only a dataset summary (observations about trends) cannot embed row-level answers; this is an architectural anti-memorization property. Not documented as intentional by the authors (inference).

### Gaps
- Exact prompt text of GenerateSingleModuleInstruction docstring truncated in my reading (tool output cap).

## 3. Anti-overfitting

### Takeaway
DSPy's protections are structural, not statistical: separate valset for selection (MIPROv2, RandomSearch), minibatch noise-robust scoring plus full eval of top-mean candidates, and the proposer never seeing labels/failures (MIPROv2). COPRO and SIMBA select on the trainset. No optimizer uses a significance test or a holdout test inside compile.

### Cited Findings
- MIPROv2 with valset=None: last `min(1000, max(1, int(0.8*len)))` of trainset become valset, first 20% remain train (already covered by other researchers). — [mipro_optimizer_v2.py L321-334](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/mipro_optimizer_v2.py#L321)
- Role split in MIPROv2: trainset -> demo bootstrapping + dataset summary + proposer context; valset -> every trial score (minibatch) and full evals. The paper's experiments instead optimize on the 500 "train" set (full evals on train) and report on a 2000-example test; Dev split was "used as a development set to internally iterate on methods", not for optimization. — [arXiv 2406.11695 App. B.1 Table 3, s5.1](https://arxiv.org/abs/2406.11695) (preprint)
- Paper table 2 reports Train/Dev/Test per task, showing generalization gaps remain: e.g. MIPRO on Iris Train 98.4 vs Test 88.6, HotPotQA 49.0/43.9/46.4 (train/dev/test). — [arXiv 2406.11695 Table 2](https://arxiv.org/abs/2406.11695) (preprint; PDF text extraction)
- Statistics: paper uses 5 runs per method and Wilcoxon signed-rank tests across test examples (not in code). — [arXiv 2406.11695 s5.2](https://arxiv.org/abs/2406.11695)
- Noise argument for minibatching: "Bayesian optimization is known for its robustness to noise... We therefore propose evaluating over mini-batches". — [arXiv 2406.11695 s4.3](https://arxiv.org/abs/2406.11695)
- SIMBA: step scores are on the same minibatch used to find failures and write rules (selection and mining share data); final selection on FULL trainset; no heldout. — [simba.py L229-310](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/simba.py#L229)

### Inferences
- Applicable ideas for AutoPrompter: (a) hidden valset for acceptance, (b) minibatch + periodic full-eval gating, (c) proposer sees dataset-level summary or aggregated error categories, not raw labelled rows, (d) record train-vs-holdout gap as a first-class metric.

### Gaps
- No DSPy code-level overfitting detector or train/val gap reporting found.

## 4. Cost per run

### Takeaway
MIPROv2 prints an estimate of calls; light/medium/heavy imply low hundreds to a few thousand task-LM calls and a few dozen prompt-LM calls; COPRO and BootstrapRS scale with candidates x dataset size.

### Cited Findings
- MIPROv2 `_estimate_lm_calls`: prompt-model calls = 10 (data summarizer) + num_instruct_candidates x num_predictors + (num_predictors+1 if program-aware); task-model calls = minibatch_size x num_trials + len(valset) x (num_trials // full_eval_steps + 1) when minibatching, else len(valset) x num_trials. — [mipro_optimizer_v2.py L222-278](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/dspy/teleprompt/mipro_optimizer_v2.py#L222) (CODE)
  - Worked example (my arithmetic): light, 1 predictor, demos on: 10 trials, minibatch 35, valset 100: 35*10 + 100*(10//5+1=3) = 650 task calls; prompt calls = 10 + 3*1 + 2 = 15 (n_instruct = int(6*0.5)=3). Bootstrapping adds extra task calls (not in the estimate).
- BootstrapRS: 16 candidates + 3 baselines each evaluated on the valset -> about 19 x len(valset) task calls plus bootstrapping runs. (derived from code)
- COPRO: depth x breadth x len(trainset) evals as above.
- SIMBA: per step bsize*num_candidates rollouts (32*6=192) + up to 7 new candidates x 32 evals + rule LLM calls; plus final 7 x len(trainset) full evals. (derived from code)

## 5. Reported gains

### Takeaway
MIPROv2 paper: joint instruction+demo optimization wins 5 of 7 tasks, up to 13% accuracy gain, with demos (Bootstrap RS) often giving most of the gain; instruction-only gains are smaller and mostly on tasks with hidden conditional rules. DSPy paper: bootstrapped few-shot lifts GSM8K from 25 to 49-88% depending on program. AdalFlow's own paper reports 93.75% vs 84.5% (TextGrad) on ObjectCount. All are preprints/author-run.

### Cited Findings
- MIPROv2 abstract/intro: "outperforms baseline optimizers on five of seven tasks in our benchmark, by as much as 13% accuracy improvement". Setup: GPT-3.5 proposer (temp 0.7), Llama-3-8B task model, GPT-4o teacher for ScoNe and HoVer, 5 runs each, Wilcoxon tests; budgets 20-50 full-eval trials (50 for HotPotQA/ScoNe ~ 300 minibatch trials, 30 for Iris/Heart/HotPotQA Cond, 20 for HoVer). — [arXiv 2406.11695 s1, s5, App B.2](https://arxiv.org/abs/2406.11695) (preprint)
- Table 2 (Train/Dev/Test, mean of 5 runs; text-extracted from PDF so verify against paper before quoting). Un-optimized baseline: ScoNe 57.0/56.2/69.1; HotPotQA 35.4/31.8/36.1; HoVer 30.2/30.8/25.3. 0-shot MIPRO: ScoNe test 71.5, HotPotQA 36.8, HoVer 33.1. Bootstrap RS: ScoNe 75.4, HotPotQA 45.8, HoVer 37.2. MIPRO (both): ScoNe 79.4, HotPotQA 46.4, HoVer 39.0. HotPotQA Conditional (hand-made rules): baseline test unclear in extraction; 0-shot MIPRO 14.6, Bootstrap RS 10.4, MIPRO 23.3. — [arXiv 2406.11695 Table 2](https://arxiv.org/abs/2406.11695) (preprint)
- Split sizes (already covered elsewhere): HotPotQA 500/500/2000, ScoNe 500/500/1200, HoVer 500/500/1520, HotPotQA Conditional 500/200/200, Iris 75/NA/75, Heart Disease 120/NA/183. — [arXiv 2406.11695 Table 3](https://arxiv.org/abs/2406.11695)
- Lessons: demos alone often beat instruction-only; instruction optimization matters for tasks with conditional rules not expressible by few-shot examples; "Bootstrap RS beats the best instruction-only optimizer for a given task in all but one case" (the exception is HotPotQA Conditional). — [arXiv 2406.11695 s6](https://arxiv.org/abs/2406.11695)
- DSPy paper Table 1 (GSM8K): GPT-3.5 vanilla 24.0 dev / 25.2 test with no compilation; vanilla+bootstrap x2 64.7 dev / 61.7 test; CoT+bootstrap 80.3 dev / 72.9 test; CoT+bootstrap+ensemble 88.3 dev / 81.6 test; reflection+bootstrap 83.0 dev / 76.0 test. Llama2-13b-chat vanilla 7.0/9.4 -> up to 49.0 dev. Note dev-test gap of ~7-8 points on several rows. Abstract claims "from 33% to 82% (Sec 6) and from 32% to 46% (Sec 7) for GPT-3.5". — [arXiv 2310.03714 Table 1](https://arxiv.org/abs/2310.03714) (preprint; ICLR 2024 per common citation, not verified here)
- DSPy docs guidance (covered elsewhere): ~10 examples BootstrapFewShot, 50+ RandomSearch, 200+ and 40+ trials for MIPROv2 "to prevent overfitting". — [optimizers.md L82-92](https://github.com/stanfordnlp/dspy/blob/bc8af7ed3d5ee0b892211e5c03274396442a413c/docs/docs/learn/optimization/optimizers.md#L82)

### Inferences
- Paper numbers show instruction-only optimization (0-shot MIPRO, OPRO) typically adds only a few points on in-distribution QA, and demos give more; this supports treating "instruction text" as the weaker lever and suggests that for our system, selection discipline matters more than proposer sophistication.

### Gaps
- No MIPROv2 result with a small trainset (< 100) was found in the paper; claims about small-data behavior are only the doc guidance.
- Table 2 baseline row for HotPotQA Conditional test shows "6" in extracted text (likely garbled decimals).

## 6. Code entry points, metric plug-in, output artifact (DSPy)

### Takeaway
All optimizers share `compile(student, trainset=..., [valset=...])` returning a copy of the program; metric is a plain Python function; artifact is `program.save(path)` JSON of instructions+demos (plus `candidate_programs`/`trial_logs` attributes in memory).

## 7. AdalFlow: loop, feedback, acceptance, cost, gains

Source pin: SylphAI-Inc/AdalFlow commit 810de99d. Permalink base: https://github.com/SylphAI-Inc/AdalFlow/blob/810de99d86191b3aa0c939aa6d6d1a21977555aa/ . Paper: LLM-AutoDiff, arXiv 2501.16673 (preprint, SylphAI authors, self-benchmarked).

### Takeaway
AdalFlow's default text-grad loop ("constrained" strategy) is a SINGLE-candidate hill climb, structurally the closest to AutoPrompter, but every candidate must pass a two-stage gate: it must beat the score on the current small error-heavy minibatch AND strictly beat the best score on a REQUIRED separate validation set before being accepted, else revert and retry (up to 5 proposals per step, with failed proposals shown to the optimizer). Test set is only used for reporting. Few-shot demos are optimized by a separate DSPy-style bootstrap optimizer gated by the same validation check.

### Cited Findings
**Loop and acceptance (code)**
- Trainer requires `val_dataset` (raises ValueError if absent); train set supplies minibatches and demos, val set "will be used to select the final prompt or samples", test set only for evaluation. Defaults: strategy="constrained", train_batch_size=4, max_steps=1000, max_proposals_per_step=5, batch_val_score_threshold=1.0, correct_val_score_threshold=0.5, max_error_samples=2, max_correct_samples=2. — [trainer.py L42-190, L418-520](https://github.com/SylphAI-Inc/AdalFlow/blob/810de99d86191b3aa0c939aa6d6d1a21977555aa/adalflow/adalflow/optim/trainer/trainer.py#L42) (CODE)
- `_fit_text_grad_constraint`: for each train batch (shuffled, size 4): forward pass -> per-sample loss (eval_fn score + LLM backward feedback) -> accumulate into a moving batch (downsampled to at most 20 samples, keeping at least 4 errors) -> sample a subset of up to 2 errors + up to 2x(num errors) correct (max 2) -> `subset_loss.backward()` (backward engine LLM writes textual gradients) -> loop up to 5 proposals: (a) `TGDOptimizer.propose()` writes a new prompt, (b) check on the subset: pass if new score > subset score (or equal and subset score >= 1.0), (c) if passed, run full validation set; accept only if `val_score > last_val_score` (strict) and call `step()` + add to history; otherwise `revert()` and record the failed proposal. If none of 5 accepted: gradients zeroed, "steps from last improvement" incremented (shown to optimizer: "Update the value more rapidly when steps are larger than 3"). — [trainer.py `_text_grad_constraint_propose_step` L2105-2316](https://github.com/SylphAI-Inc/AdalFlow/blob/810de99d86191b3aa0c939aa6d6d1a21977555aa/adalflow/adalflow/optim/trainer/trainer.py#L2105) (CODE)
- Full validation runs with `minimum_score=last_val_score` (early abort hook when the candidate cannot beat the best). Stop condition: max_steps only (no stagnation stop; stagnation raises optimizer urgency). Initial val (and test) score of the seed prompt computed in `_pre_fit`; best checkpoint = highest val score; ckpt JSON saved each step. — [trainer.py L705-733, L831-843](https://github.com/SylphAI-Inc/AdalFlow/blob/810de99d86191b3aa0c939aa6d6d1a21977555aa/adalflow/adalflow/optim/trainer/trainer.py#L705)
- Other strategies in same file: "random" (no minibatch check), "mix" of text+demo, TSGD-M (momentum + cache of prompts, minibatch evaluation of cached prompts) and `TrainerGumbel` (Gumbel-top-k selection of prompts by score stats). README markets "Stable, scalable prompt optimization using momentum-weighted textual gradient" and "Gumbel-Top-k sampling improves exploration". — [trainer.py L2530-3207](https://github.com/SylphAI-Inc/AdalFlow/blob/810de99d86191b3aa0c939aa6d6d1a21977555aa/adalflow/adalflow/optim/trainer/trainer.py#L2530), [README L259-263](https://github.com/SylphAI-Inc/AdalFlow/blob/810de99d86191b3aa0c939aa6d6d1a21977555aa/README.md#L259) (README-only for effectiveness claims)

**Feedback and proposer prompt (code)**
- Per-sample textual gradient: `EvalFnToTextLoss` + backward engine. Backward prompt asks an LLM to "determin[e] the root cause", uses the ground truth ("based on the expected correct response (y_gt/ground_truth) and the score... Specify the difference between the expected correct response and the response") and "Maximum 3 sentences", "Be CONCISE". Comment: "not receive feedback for good performing case is important for performance". — [backend_engine_prompt.py](https://github.com/SylphAI-Inc/AdalFlow/blob/810de99d86191b3aa0c939aa6d6d1a21977555aa/adalflow/adalflow/optim/text_grad/backend_engine_prompt.py#L1) (CODE)
- Proposer (`TGDOptimizer`, `tgd_optimizer.py`): system prompt "refine a variable/prompt based on feedback from a batch of input data points", must use ONE of four edit methods (add, add examples, rephrase/replace, delete) plus one of six prompting techniques; "Batch Awareness: ... ensure the change applies to the whole batch (except while using demonstration)". User message includes: variable and peer info, system variables, top `max_past_history` (default 3) past prompts with their val scores ("generate new variable that score higher than all past iterations"), up to `max_failed_proposals` (default 5) failed proposals of the current step ("same batch, same feedback... You MUST approach differently"), the gradients (feedback text) for the sampled batch, optional constraints, steps-since-improvement. LLM cache is turned off for proposals. If proposal equals current value it is treated as a no-op. — [tgd_optimizer.py L60-125, L357-420, L545-690](https://github.com/SylphAI-Inc/AdalFlow/blob/810de99d86191b3aa0c939aa6d6d1a21977555aa/adalflow/adalflow/optim/text_grad/tgd_optimizer.py#L60) (CODE)
- History is deduplicated by exact value (same prompt re-added replaces old entry) and kept sorted by val score, pruned to top-k. — [tgd_optimizer.py L464-481](https://github.com/SylphAI-Inc/AdalFlow/blob/810de99d86191b3aa0c939aa6d6d1a21977555aa/adalflow/adalflow/optim/text_grad/tgd_optimizer.py#L464)

**Paper (LLM-AutoDiff, preprint)**
- Describes the same protocol: split (Dtrain, Dvalidate, Dtest); "A new prompt is generated if validation on Dvalidate improves"; compute gradients only for samples below threshold tau (error samples); two-stage validation (minibatch then full val) "prevents the frequent and costly full-dataset evaluations"; up to n_p candidate prompts per backward pass in a "beam-like" way; "no errors in batch" probability can exceed 40% at 80% accuracy, N=50, n=4, where proposals would "merely rephrase existing prompts". — [arXiv 2501.16673 s3.2, s3.4](https://arxiv.org/abs/2501.16673) (preprint)
- Setup: gpt-3.5-turbo-0125 forward engine; GPT-4o as backward engine and optimizer; 12 training steps, batch size 4; checkpoint chosen by validation accuracy. Splits: ObjectCount 50/100/100 train/val/test; TREC-10 120/166/344; HotPotQA RAG variants 50 "hard" train queries, 100 val, 200 test. MIPROv2 baseline configured with num_candidates=12, init_temperature=1.0 (no `auto` preset), GPT-4 prompt model. — [arXiv 2501.16673 s4.1](https://arxiv.org/abs/2501.16673) (preprint)
- Results Table 2 (start -> val/test): ObjectCount Ours 96.5 val / 93.75 test (start 86/83) vs TextGrad 95.25 / 84.5 vs DSPy(5+2) 84 / 82.5; TREC-10 Ours 86.9/87.5 vs TG 83.73/84.88 vs DSPy(5+2) 86.4/81.7; Vanilla RAG HotPotQA EM Ours 47/43.25 vs DSPy(4) 40.5/42.4; Multi-hop RAG Ours 56.25/48.25 vs DSPy(2+2) 47.25/50.63 (DSPy higher on test there); Agentic RAG Ours 35.5/32.25 from 15/16.5 start. - README claims "Token-efficient and better performance than DsPy" (marketing; supported only by the authors' paper). — [README L259](https://github.com/SylphAI-Inc/AdalFlow/blob/810de99d86191b3aa0c939aa6d6d1a21977555aa/README.md#L259) (README-only)

**Cost (derived)**
- Per step: forward on batch (4) + backward LLM calls for error samples (one per sample, GPT-4o class) + up to 5 proposals; each proposal costs 1 optimizer call + a subset eval (<= 4 samples) and, if passed, a full val pass (|val| calls, with early-abort via `minimum_score`). Paper says a TextGrad backward pass on 4 samples "can take up to 70 seconds" and one proposal ~10 s. — [arXiv 2501.16673 s3.4](https://arxiv.org/abs/2501.16673) (preprint); step breakdown is my reading of trainer.py.

### Inferences
- AdalFlow is basically AutoPrompter's loop plus: required validation split with strict-improvement acceptance, a cheap minibatch pre-gate (reduces expensive full evals), small error-focused samples (2 errors + <=4 correct) instead of whole-dataset feedback, a short best-K history, a "failed proposals this step" list, and revert-on-reject. The failure-driven feedback includes ground truth, so label leakage into prompts is possible in AdalFlow too; its defenses are the val gate and the "apply to the whole batch" wording, not a code-level label filter (I did not find one).
- Val-gated hill climbing on a small val set still overfits to val (paper: val 96.5-98 vs test 93.75 on ObjectCount; TG 95.25 vs 84.5). A bootstrap significance test for acceptance (as we have) is an addition neither system uses.
- Selecting the best checkpoint by val and reporting on test is the standard practice used in both frameworks' papers/code.
